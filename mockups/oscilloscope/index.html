Oscilloscope
Panel Studies

Four interfaces for the same instrument: a browser oscilloscope fed either by a dropped audio file or live from the soundcard. Each panel below is live — the same synthetic two-channel source runs through the same renderer in all four, so what differs is the layout and the control philosophy, not the drawing. Turn the knobs, press the keys, switch the modes.

Why it works

It is the picture in everyone's head when you say "oscilloscope", and it suits a site built out of retro desktop furniture. Every control is visible at once — no menus, no modes hidden two levels down — which is genuinely faster once learned.

The panel is also the most fun to build: rotary switches with printed value rings, a lever for display mode, real phosphor persistence on the trace.

Where it hurts

Knobs are a poor input device with a mouse, and worse with a thumb. Reading "500 mV/div" means counting ticks around a ring rather than reading a number.

FFT and measurements have nowhere to live. The real 465 had neither; here they arrive as a fictional plug-in and a display mode, which is a fudge.

Where the brief lands

  • ScalingVOLTS/DIV and TIME/DIV rotary switches, 1-2-5 rings
  • TriggerLEVEL knob + SLOPE / MODE / SOURCE switches
  • Rollthe extreme anticlockwise position of TIME/DIV
  • X-Ybottom position of the DISPLAY MODE lever
  • FFT"Spectrum" button, dressed as a 7L5 plug-in

Why it works

This is the layout that already solved the problem. Every requirement in the brief has an obvious home, because a real DS-1000 has all of them: roll is a horizontal timebase mode, X-Y is a display mode, FFT is a maths function.

The screen carries its own status strips, so the readouts are legible at any window size and stay legible when the panel is scaled down on a phone.

Where it hurts

It is a lot of chrome for a web app — roughly 30 controls, most of which do nothing until wired up. There is a real risk of building the furniture and running out of appetite before the signal path is good.

It is also the least ClackOS-looking of the four: a grey Chinese bench instrument sitting inside a cream retro desktop, ignoring the theme entirely.

Where the brief lands

  • ScalingCH1/CH2 Scale + Horizontal Scale knobs, values on screen
  • TriggerLevel knob, 50 % / Force keys, Trig Menu softkeys
  • RollHoriz Menu → Time Base → Roll
  • X-YHoriz Menu → X-Y (or Display → Format)
  • FFTMath → FFT, with window and vertical-scale softkeys

Why it works

It is the best-looking of the four by a distance, and the cheapest to build — six knobs, two toggles, no menu system, no readouts to keep in sync.

The round tube with real afterglow is a genuinely lovely thing to watch audio through, and X-Y on a round screen is the classic stereo vectorscope picture.

Where it hurts

A round screen throws away a third of the pixels, and a spectrum display inside a circle is actively bad — the frequency axis runs into curved glass at both ends.

No numbers anywhere means no measurements, and "which volts per division am I on" can only be answered by looking at a knob.

Where the brief lands

  • ScalingVERT GAIN and SWEEP RANGE rotaries, ×1 ×10 ×100
  • TriggerSYNC level knob + slope toggle; no trigger modes
  • RollMODE position 3
  • X-YMODE position 2 — the tube's native trick
  • FFTMODE position 4, and it fights the round screen

ClackOS Native

No imitation: a ClackOS application that happens to be a scope. Menu bar, theme variables throughout, keyboard-reachable controls, numbers you can read. This is the only study that changes with the page theme — switch your system to dark and watch just this panel follow.

Why it works

It obeys the house rules: theme variables so all twelve palettes apply, real form controls so it works with a keyboard and a screen reader, a menu bar built the way every other app on the desktop builds one.

Measurements are free here — there is a panel to put them in. Adding cursors, a second maths trace or a file transport later costs nothing structurally.

Where it hurts

It has no character. Sat next to the other three it looks like a settings dialogue with a picture of a waveform, and the site's whole personality is that its apps look like the machines they descend from.

A sidebar of dropdowns is also the slowest way to change gain while watching a signal — the one thing you do constantly on a scope.

Where the brief lands

  • Scalingsteppers in the sidebar, plus scroll-over-screen
  • Triggerlevel slider with a live number, slope + mode selects
  • Rollmode segment under the screen
  • X-Ymode segment under the screen
  • FFTmode segment under the screen

Recommendation

Build B's information design in D's clothes

B is the only layout where all five requirements already have a home, because a real DSO solved this problem forty years ago: the screen carries the numbers, the softkey column carries whichever menu is open, and roll / X-Y / FFT are ordinary entries in it. D is the only study that obeys the site's own rules about themes, keyboards and window sizes. They are not in conflict — B is an information design, D is a skin.

So: take the DSO arrangement — status strip along the top of the screen, channel and timebase bar along the bottom, six softkeys down the right bezel, hard keys grouped by function — and draw all of it from the ClackOS theme variables instead of grey plastic. The trace colours come from --series-1 and --series-2, the screen ground from --ink, the panel from --paper.

A and C are the fun ones and should not be thrown away. Both are skins over the same renderer: the same canvas, the same signal path, a different set of controls bound to the same state object. If the state lives in one place from the start, "Appearance → Scope panel: 465 / Oscillograph / ClackOS" is an afternoon's work later, not a rewrite.

If this is the direction, next steps

  1. Signal path first, panel second. getUserMedia plus an AudioWorklet ring buffer, and a decodeAudioData path for a dropped file — with a test-tone generator so the panel can be developed with no input.
  2. One state object, one renderer. Mode, s/div, V/div per channel, trigger level / slope / mode, position, persistence. Every control writes to it; the canvas reads it. This is what makes the skins cheap.
  3. Trigger on the buffer, not on time. Hunt the crossing inside the captured block, with hysteresis, and hold the last good position when the crossing is lost — that is the difference between a scope and a wiggling line.
  4. FFT via the real thing. AnalyserNode.getFloatFrequencyData for the live path; a hand-rolled radix-2 for file playback, so both paths agree.
  5. Register it properly. content/applications/scope.html, a Multimedia entry in menu.json with allow: "microphone", its own description for crawlers, then build_app_metadata.py and build_plain_site.py.
